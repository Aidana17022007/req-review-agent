# Требования как код: ReqLens в каждом Pull Request

Документ требований живёт в репозитории рядом с кодом. Аналитик меняет `docs/*.md` (или `.pdf`, `.docx`) в Pull
Request. ReqLens проверяет обе версии документа: из ветки PR и из base. Потом оставляет в PR **один** комментарий и
обновляет его при каждом новом коммите. В комментарии:

- вердикт «Разработка / Тестирование» было → стало;
- число критичных дефектов и всех замечаний было → стало;
- **новые дефекты** — появились в PR, с дословной цитатой и строкой;
- **исправленные дефекты** — были в base, в PR их нет;
- ссылка на артефакт прогона с полным отчётом (md, html, pdf).

Замечания сравниваются по критерию и нормализованной цитате, поэтому сдвиг строк и перенумерация требований не дают
ложных «новых» дефектов. Комментарий не длиннее 60 строк, остальное спрятано в `<details>`.

## Подключение в репозитории банка — 3 шага

1. **Скопировать агента и workflow.** Положите в репозиторий каталог агента (`req_review/`, `review.py`,
   `scripts/pr_comment.py`, `requirements.txt`) и файл `.github/workflows/requirements-review.yml`. Можно и
   отдельным шагом `actions/checkout` репозитория ReqLens. Документы требований храните в `docs/`.
2. **Добавить секрет (по желанию).** Settings → Secrets and variables → Actions → `GEMINI_API_KEY`. Без секрета бот
   работает в режиме `LLM_PROVIDER=rules`: только детерминированные правила, без отправки текста во внешнюю модель.
   Так и пишется в комментарии. В закрытом контуре можно указать свою модель через `.env` (Ollama и другие
   OpenAI-совместимые серверы, см. README «Запуск без интернета»).
3. **Включить шлюз качества (по желанию).** Settings → Variables → `REQ_GATE=1`. Тогда проверка PR становится
   «красной», если в PR появился новый критичный дефект. Затем отметьте проверку «Requirements review» как
   обязательную в правилах защиты ветки.

Права workflow минимальные: `contents: read`, `pull-requests: write`. Ключ берётся только из `secrets`. Проверяется
не больше 3 документов за PR. Служебные документы проекта (README, API, SCHEMA и др.) пропускаются.

Проверить без PR: Actions → Requirements review → Run workflow (поле `document`). Локально:

```bash
LLM_PROVIDER=rules python review.py base.md base/report.md --no-html
LLM_PROVIDER=rules python review.py pr.md pr/report.md
python scripts/pr_comment.py --new pr/report.json --old base/report.json --doc docs/requirements.md --rules-only --gate
```

`--gate` возвращает код 1 при новом критичном дефекте.

## Пример комментария

Это настоящий вывод `scripts/pr_comment.py`, режим правил, без модели. Взят документ организаторов
(`bench/real/notifications.md`) и две правки:

- метод сохранения переведён с GET на PUT — это исправление;
- добавлено требование «Ф-5 … TBD» — это новый критичный дефект.

````markdown
<!-- reqlens-pr-review -->
## ReqLens · ревью требований: `docs/requirements.md`

| | Было (base) | Стало (PR) |
|---|---|---|
| Разработка | нельзя | **нельзя** |
| Тестирование | нельзя | **нельзя** |
| Критичных дефектов | 6 | **6** |
| Всего замечаний | 27 | **27** |

**🆕 Новые дефекты (2)**
- 🔴 **Ф-5** (строка 40) — Требование содержит незаполненное место (TBD/«уточнить»). — «Лимит уведомлений для премиальных карт: TBD.»
- 🟠 **набор** (строка 37) — Критерии приёмки покрывают 40 % правил (2 из 5). Без примеров остаются: Ф-1, Ф-5, Ф-4. Приёмку нельзя провести по документу — каждый тестир… — «Держатель активной карты KZT задаёт целый порог от 1 000 до»

**✅ Исправлены (2)**
- 🔴 **набор** (строка 104) — Метод объявлен как GET («REST type | GET»), но выполняет изменение данных («Сохранение»). GET по смыслу безопасен и не меняет состояние: та… — «REST type | GET»
- 🟠 **набор** (строка 37) — Критерии приёмки покрывают 50 % правил (2 из 4). Без примеров остаются: Ф-1, Ф-4. Приёмку нельзя провести по документу — каждый тестировщик… — «Держатель активной карты KZT задаёт целый порог от 1 000 до»

Режим: только детерминированные правила (секрета GEMINI_API_KEY нет). Полный отчёт (md, html, pdf): [артефакт прогона](https://github.com/OWNER/REPO/actions/runs/123). ⛔ В PR появился новый критичный дефект.
````

Обратите внимание: число критичных осталось 6, но бот видит, что это **другие** 6. Один критичный дефект исправлен,
один новый появился, и шлюз качества останавливает PR.
